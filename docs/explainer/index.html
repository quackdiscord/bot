01

The shape of it

You come back to a project after a few months and open the repo. The first thing you notice is that it got big. A Discord bot that picks a punishment from a member's history now has 220 Go source files, a React dashboard, a 2,882-line generated Swagger contract, a 1,257-line execution plan, and the entire v4 bot still sitting in Legacy/.

That isn't a disaster. It builds, and go test ./... passes in every package. But before you simplify anything, you need to see where the weight actually is. The map below sizes every rectangle by line count. Hover a block to see what it is. Then toggle Legacy off and notice how much of what's left is the core moderation logic versus scaffolding around it.

Figure 1 · Where the code liveslines
Hover a block
Each rectangle is a package or folder, with area proportional to lines. Compare internal/quack, the domain where the escalation rules live, with everything around it: storage, two transport adapters, an integration layer, vendored UI, and docs. The core is about a tenth of the repo.

Here's the punchline up front. The domain package, internal/quack, is 7.9k lines, and it's mostly fine: small files, consistent naming, real invariants. The bloat sits around it. There are four structs per database table, an integration package that slowly became the real composition root, the same permission check done three or four times per command, and docs that describe an older version of the code. Simplifying v5 is mostly deleting and merging, not redesigning.

02

The idea

In v4, a moderator typed /warn, /timeout, or /ban and decided the punishment themselves, every time. Consistency depended on whoever was online. v5 moves that decision upstream to the admins, who decide it once, ahead of time.

Admins define the server's moderation rules. Moderators apply those rules. Quack chooses and carries out the configured result. v5.md:7

The whole product falls out of six nouns. You'll see each of them again as a Go type, a database table, and a dashboard route, so it's worth getting them straight now.

case_templates
Template
One rule, like "spam" or "harassment". It is owned by the guild and versioned, and it is archived rather than deleted.
case_template_levels
Level
A rung on the ladder. One default rung, plus rungs that trigger at case-count thresholds.
cases
Case
A moderator applied a template to a member. Freezes a snapshot of the template and the level it selected.
case_action_executions
Action
Zero or one timeout, kick, or ban per level, executed by a leased, retrying worker.
appeals
Appeal
A member asks staff to review one case. If staff accept it, they can reverse the action.
audit_log_entries
Audit log
An append-only record of everything important, optionally mirrored to a Discord channel.

v4 (Legacy/)

  • Moderator picks /warn, /kick, /ban
  • Moderator chooses duration and reason
  • Discord commands are the product
  • Many features, little cohesion

v5 (apps/backend)

  • Moderator picks a template and a member
  • Quack picks the level from history
  • Discord and dashboard share one core
  • Core: templates, cases, actions, appeals, audit

Everything else in the repo, including tickets, logging channels, honeypots, evidence capture, and v4 import, is either an optional module or plumbing that keeps those six nouns honest. Keep that in mind later when you're deciding what to cut.

03

Escalation, the core

This is the part you love, and it's genuinely small. A template has exactly one default level and any number of threshold levels, each with a distinct trigger_case_count. When a moderator applies the template, Quack counts the member's previous cases under that template, adds one for the case being created, and picks the highest threshold that count has reached. If none match, the default applies.

The count follows four rules. It is scoped to one guild, one member, and one template across all of the template's versions. Voided cases don't count, and neither do cases imported from v4. It is also all-time: there are no decay windows. Those used to exist and were deliberately removed (TODO.md:9-10).

The selection code never changes the case. It hands back a level, and buildTemplateSnapshot (case_escalation.go:78) serializes the template's name, version, reason, the selected level, its action settings, and the context fields into cases.template_snapshot_json. This is how v5 keeps the promise in v5.md that "later template edits never rewrite old cases." It also matters because template updates edit rows in place: the version increments, then levels and actions are deleted and recreated. The snapshot is the only historical copy.

key insight

The rules engine is roughly 200 lines of Go. Those are case_escalation.go plus normalizeLevels / normalizeActions in template_validation.go:121-216, which enforce one default level, distinct positive thresholds, and at most one timeout/kick/ban per level. Everything else in the backend exists to make that decision safe. That covers live Discord permission checks, a guild row lock so two moderators can't both create "case #3", durable action execution, notifications, appeals, and audit.

04

Architecture map

The backend is one Go module, apps/backend, that builds into one binary plus three maintenance tools (quack-migrate, quack-storage-verify, quack-v4-import). cmd/quack/main.go calls runtime.Run, which loads config, opens MySQL and Redis, runs migrations, and then wires everything around one quack.Services struct before blocking on the HTTP server (runtime/runtime.go:23-113).

The intended design is a clean hexagon. internal/quack holds the domain and declares "ports" (interfaces), store implements persistence, and discordbot and httpapi are two thin front doors. Mostly, that's what you got. The graph below is built from the real import statements (subpackages collapsed). Click any box to see what it owns and what's wrong with it. naming trap

discordbot/ and quack/ both have actions.go, authorization.go, audit_mirror.go, and appeal_notifications.go. These are not duplicates. The quack files are policy and orchestration, and the discordbot files are the REST calls behind them. Identical file names in two layers make that very hard to see. Renaming the adapter side (for example, rest_actions.go) costs nothing and removes most of the "is this duplicated?" confusion.

05

Life of a case

Here's the spine of the whole system. A moderator types /case add template:spam user:@someone in Discord, and twenty-odd steps later the member is timed out, DMed, and the public channel shows the result. Following that one request touches nearly every package, so it's the best way to see both the good engineering and the redundancy.

Step through it below. Each dot is a real function call on one of five lanes. Amber rings mark work that has already been done once earlier in the same request. Blue dots are database transactions. Keep an eye on the counter of live Discord lookups. Every one is a REST round-trip to Discord before a single row is written.

Figure 4 · /case add, from slash command to DMstep 0 / 0
Discord lookups: 0 · level selections: 0
Notice the moment the flow crosses from quack to store at step 10. That's the guild row lock. Everything before it runs outside the lock (and Discord calls should). Everything after it, up to the commit, is serialized per guild so case numbers and escalation counts can't race.

Two things deserve credit. First, the lock design is right. Quack does slow, external work (Discord permission refresh, evidence capture) in a preflight outside the transaction. It then takes SELECT … FOR UPDATE on the guild row (store/storage.go:26-43), re-selects the level, and compares the result with the preflight. If another case slipped in between and changed the level, the preflight is stale and the whole thing retries, up to four times (quack/cases.go:123-140). That's optimistic concurrency done properly.

Second, the redundancy is real but shallow. The Discord adapter resolves the staff context three separate times (commands/case.go:91, :95, case_create.go:35), and then PreflightCase refreshes it a fourth time. The idempotency check is duplicated, with slightly different nil handling, in createWithAttribution (cases.go:104-120) and create (case_creation.go:23-38). Pass one GuildStaffContext down and delete the copies.

06

The action engine

When a case commits, its punishment is just a row: case_action_executions.status = 'pending'. Nothing has happened in Discord yet. The comment in quack/doc.go says it plainly: "Persisted action rows are the durable work queue; in-memory submissions only reduce latency."

A worker claims a row by locking the case, flipping the row to running, incrementing attempt_count, and taking a two-minute lease with a fresh ULID token (store/action_claims.go:16-111). It runs the executor from actionmods with a 30-second timeout, then records the outcome. That write is fenced by the lease token, so a worker that lost its lease can't overwrite a newer result (store/action_results.go:15-37). Play with the outcomes below to walk the state machine.

internal/quack/actions.go:202-207the whole retry policy
func shouldRetryAction(execution model.CaseActionExecution, result actionmods.Result) bool {
	if !result.Retryable || result.OutcomeUncertain || !execution.SafeForRetry {
		return false
	}
	return execution.AttemptCount <= execution.MaxRetries
}

After the last action reaches a terminal state, the same loop moves on to the member notification (actions.go:76-77). This is a separate mini state machine on case_notifications (pending → prepared → claimed → sending → sent/failed). For kicks and bans, Quack opens the DM channel before enforcement (prepareNotification), because once the member leaves the guild you can no longer reach them.

bug · verified

Notify-only cases can lose their DM. The durable poller only looks at case_action_executions (store/action_polling.go:33-41). A case whose level has no action, which is exactly starter-policy cases 1 and 2, has zero execution rows. Its notification is reached only if the in-memory Submit succeeds. Submit drops work when the buffer is full or the queue is inactive (workqueue/queue.go:101-124), and a restart loses anything still in memory. In those cases the pending notification sits forever. The same thing happens if the process dies after the last action finishes but before the DM goes out. Fix: include due case_notifications in ListExecutableCaseIDs, or model the DM as an execution row.

07

Surfaces & modules

There are three ways in. The Discord bot exposes a single /case command tree (with autocomplete and a modal for template context fields) plus buttons for appeals and tickets. The old /warn, /kick, and /ban are intentionally gone. The HTTP API serves the dashboard with cookie sessions from Discord OAuth, CSRF double-submit, Redis rate limits, and Idempotency-Key on writes. Every guild route goes through RequireGuildContext(capability), which re-checks live Discord permissions (middleware/guild.go:33). The dashboard is TanStack Start + React 19 + coss UI, with routes for cases, templates, appeals, action failures, audit log, settings, and a member-facing "my cases / appeal" view.

bug · verified

The dashboard's module switches do nothing. The settings form writes tickets_enabled, general_logging_enabled, and honeypot_enabled to guild_settings (settings-form.tsx:27-56, quack/settings.go:228). The modules gate on a different table entirely, module_configurations.enabled (for example honeypot/service.go:202). No code reads the guild_settings flags at runtime, and the dashboard never calls any /modules/* endpoint. Pick one source of truth and delete the other.

08

Storage

MySQL through GORM, Redis for sessions, OAuth state, and the command-hash cache, and SQLite only in tests. There are 30 tables, created by 11 checksummed migrations that run at startup under a MySQL GET_LOCK. The core is ten tables you'd draw on a whiteboard: guilds, guild_settings, the three case_template* tables, cases, case_action_executions and case_action_attempts, case_notifications, and audit_log_entries. Appeals, evidence, tickets, honeypots, and import bookkeeping make up the rest.

The store is solid where it counts. It has transactions with row locks, lease fencing, unique idempotency keys on cases, executions, notifications, and appeals, and audit rows written in the same transaction as the change they describe. Where it gets heavy is representation. One table can be described by up to four Go structs: a frozen copy inside its migration, a *Record type (13 of 18 are used only by tests), the domain struct that GORM also queries directly, and occasionally a second record type for the same table. The domain model even carries a GORM tag, so the field called Validity is stored in a column called status (quack/model/schema.go:276).

compatibility for what, exactly?

A surprising share of store exists to preserve earlier v5 data. There are quarantine tables for "incompatible" templates and cases (migrations 0002/0003), dead columns (window_minutes, continue_on_error, timeout_ms, default_severity, severity and weight on cases), and a write-only action_manual_reviews table. Meanwhile the readiness doc says v5 has never run against a real guild. If no production v5 database exists, you can squash all 11 migrations into one clean baseline and delete the whole compatibility layer.

Two smaller structural notes. quack.Repository is a 63-method interface built by embedding ten smaller ports that overlap heavily (CreateAuditLogEntry appears in nine of them), and nothing asserts at compile time that *store.Store satisfies it. Some business rules also live in the store: the starter policy contents, which actions are reversible, when a lease-expired action is unsafe to rerun, and appeal eligibility parsed out of snapshot JSON. Those belong in quack.

10

A simpler v5

The good news is that none of this calls for a rewrite. The domain model already matches v5.md, the escalation logic is tiny and correct, and the concurrency story (guild lock, leases, lease-fenced writes) is the hard part, and it's done. A cleaner v5 keeps all of that and sheds much of the code around it. Here's an order that keeps the tests green at each step.

Fix the two real bugs first

Make the poller find due notifications, so notify-only cases always get their DM. Then collapse the module switches onto module_configurations and either wire the dashboard to /modules/* or remove the toggles.

small · user-visible

Delete what nothing calls

Remove SkipCaseActions and the skipped status, the module-level migrations and v4 importers that only tests use, the 13 test-only *Record types, quack.DiscordEnforcementClient, the unused embed helpers, and routes.SetupRoutes. Then decide whether Legacy/ belongs in this repo at all, since it declares the same module path.

small · zero behavior change

Squash storage to one shape per table

If no production v5 database exists, replace migrations 0001-0410 with one baseline. Drop the quarantine tables and dead columns, rename cases.status to validity, and keep exactly one record struct per table, mapped explicitly to the domain types. This is the biggest line-count win.

medium · needs a yes/no on production data

Untangle moduleintegration

Move the appeal dispatcher, audit mirror, and /case button handlers into runtime (or a core Discord registrar). Let each module own its own Discord and HTTP adapter behind small registrar interfaces, so httpapi no longer imports moduleintegration and nothing imports back into httpapi.

medium · pure refactor

Thread one context through each request

Resolve the GuildStaffContext once per Discord interaction and once per HTTP request. Merge the duplicate idempotency checks. Build httpplatform.Primitives once and pass it down instead of sniffing any for Redis() four times. Replace the 63-method Repository with the small ports, plus a var _ = compile-time assertion.

medium · fewer Discord REST calls per command

Move rules up, keep the store dumb

Starter policy content, reversal eligibility, retry-safety, and appeal eligibility move into quack. Drop the config and discordgo imports from the core. Collapse SafeForRetry/Irreversible into one flag, since today every template action sets both the same way.

medium

Cut the docs to two files

Keep v5.md (product truth) and one accurate architecture.md regenerated from this review. Archive the exec plans, scope-drift log, and integration notes. Fix the README pointers (openapi.yaml → swagger.yaml, and the dashboard is no longer empty). Generate api-types.ts from the Swagger contract instead of hand-writing it, and pin the dashboard's "latest" dependencies.

small · stops the drift from coming back
the takeaway

Your instinct is right: the idea is solid and the core is small. The messiness is mostly scaffolding that outlived its purpose: compatibility layers for data that may not exist, an integration package that absorbed core wiring, and repeated permission checks. Strip those and v5 is a ~200-line rules engine with a durable, well-fenced action worker and two thin front doors, which is exactly what v5.md describes.
