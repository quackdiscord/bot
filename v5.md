# Quack v5

Quack v5 is a customizable moderation system for Discord servers.

Its central rule is simple:

> Admins define the server's moderation rules. Moderators apply those rules. Quack chooses and carries out the configured result.

This document defines what Quack v5 is. It is the source of truth for product behavior and scope. If code, technical documentation, or a backlog disagrees with this document, that difference is scope drift. Intentional product changes must update this document before implementation begins.

This is not a roadmap or progress report. It does not say which features are finished or how the code is organized.

## The Main Ideas

Quack uses a few simple building blocks:

- A **template** is a moderation rule for one kind of problem, such as spam or harassment.
- A **level** describes what should happen as the same member receives more cases from that template.
- A **case** records that a moderator applied a template to a member.
- An **action** is the Discord enforcement chosen by a level: timeout, kick, or ban.
- An **appeal** asks staff to review a specific case.
- The **audit log** is the permanent record of important activity in Quack.

Templates hold the decisions that moderators previously had to make themselves. A moderator chooses the right template and provides the requested context. Quack checks the member's history, chooses the correct level, creates the case, performs the configured action, and records what happened.

## How v5 Differs From v4

Quack v4 provided many useful Discord commands, but servers had limited control over how those commands worked together. Moderators often chose the punishment and entered its details each time.

| Quack v4 | Quack v5 |
| --- | --- |
| Moderators chose commands such as `/warn`, `/timeout`, `/kick`, or `/ban`. | Moderators choose an admin-defined template for the rule that was broken. |
| Moderators decided which punishment fit the situation. | Quack selects the configured level from the member's history. |
| Moderation flows depended on commands and moderator judgment. | Admins define consistent flows before an incident occurs. |
| Discord was the main product surface. | Discord and the dashboard use the same Quack behavior and records. |
| Features were broad but difficult to customize as one system. | The core stays focused on templates, cases, actions, appeals, and audit history. |

The old direct moderation commands are not equal workflows in v5. After migration, `/warn`, `/timeout`, `/kick`, and `/ban` are removed in favor of applying templates.

## Product Principles

### The guild owns its rules

Quack does not decide what good moderation looks like for every server. Admins control the templates, levels, reasons, actions, appeal choices, and requested context for their guild.

Quack may provide starter rules, but admins can edit, replace, export, import, or archive them.

### Moderators apply rules instead of inventing them

Moderators identify the rule that was broken, choose the matching template, choose the member, and provide the requested context. They do not choose the escalation level, rewrite the official reason, or replace the configured action.

### Discord remains the authority for access

Discord owns guild identity, membership, roles, permissions, and role hierarchy. Quack does not create a second staff-role system.

### History must remain understandable

A case keeps a copy of the template version, selected level, reason, context, evidence, action, and result used at the time. Later template edits never rewrite old cases.

### Guild data stays inside the guild

Templates, cases, appeals, audit entries, and escalation history belong to one Discord guild. A member's history in one guild never affects another guild.

### Important records are not hard-deleted

Normal product behavior never permanently deletes cases or audit entries. Incorrect cases are voided and remain visible for accountability.

## People and Permissions

Quack checks current Discord permissions before sensitive operations. Cached information may support displays, but it does not grant lasting access after a Discord role changes.

### Guild owner and Administrator

The guild owner and members with Discord `Administrator` have full access to Quack for that guild.

### Manage Guild

Members with Discord `Manage Guild` can:

- Create, edit, import, export, and archive templates.
- Configure the audit mirror and optional modules.
- Manage guild-wide Quack settings.

### Moderate Members

Members with Discord `Moderate Members` can:

- Apply templates and create cases.
- Review cases and member case history.
- Read the complete audit log.
- Review appeals.
- Void cases with a required reason.
- Dismiss failed-action alerts without removing their history.

### Action permissions

Creating a case does not grant extra Discord power. If the selected level contains an action, the moderator must also have the matching Discord permission:

- Timeout requires `Moderate Members`.
- Kick requires `Kick Members`.
- Ban requires `Ban Members`.
- Retrying an action requires the same permission as the original action.

The moderator and Quack bot must also be high enough in the Discord role hierarchy to act on the target.

If the moderator lacks permission for the level Quack selects, Quack blocks the entire request before creating a case. It never creates a partial case with the configured action silently removed.

When a moderator loses the required Discord role or permission, access ends on their next sensitive request. Their earlier actions remain attributed to them in history.

## Dashboard, Discord, and the Backend

The dashboard and Discord are two ways to use the same Quack behavior. They do not maintain separate moderation rules or case logic.

### Dashboard

- Admins build templates and configure the guild.
- Moderators apply templates, provide detailed context, search cases, review failures, and review appeals.
- Members view their own cases and appeals.

Members sign in with Discord. They may view cases targeting their Discord identity even after leaving or being banned from the guild. This access never exposes other members or wider guild data.

### Discord

- Moderators apply templates quickly while working in the server.
- Moderators review cases and member history.
- Message context actions capture evidence from a live message.
- Case notifications and buttons lead members into the dashboard appeal flow.

Template creation, editing, import, export, archive, and module configuration remain dashboard-only. Discord may show template summaries, but it is not a second template builder.

### HTTP API

The HTTP API supports Quack's dashboard and internal adapters. It is not a promised public integration or automation platform in v5.

## Templates

A template represents an infraction or moderation rule, not a punishment.

Good template examples include:

- General rule violation.
- Spam.
- Harassment.
- Advertising.
- Posting disallowed content.

Templates named only after punishments, such as “ban” or “timeout,” recreate the v4 workflow and should not be the normal model.

A template defines:

- A name and short description.
- A fixed official reason shown to the member.
- Whether its cases can be appealed.
- The context fields a moderator must complete.
- One default level.
- Optional higher levels based on case count.
- Whether each level notifies the member.
- Zero or one enforcement action for each level.

Moderators cannot replace the official reason. Submitted context appears separately from the reason.

### Template identity and versions

Editing a template creates a new version of the same rule. Earlier non-voided cases from that template still count toward escalation, even when they used older versions.

Every case stores a snapshot of the version it used. This keeps old decisions understandable after an admin changes the template.

### Active and archived templates

Archive is the only template availability control.

- A valid saved template is active immediately.
- An active template can be applied to create cases.
- An archived template cannot create new cases.
- Archived templates and their cases remain visible.
- An admin can restore an archived template.

There is no separate enabled switch, draft state, or approval workflow. Draft work remains in the dashboard until it is saved.

### Import and export

Admins can export and import template definitions.

An export contains moderation rules only. It never contains:

- Guild or Discord channel IDs.
- Cases or member history.
- Audit entries.
- Tokens, secrets, or private module settings.

An imported template becomes a new template identity owned by the receiving guild. A valid import becomes active after the admin confirms it.

## Escalation Levels

Every template has exactly one default level. The default level applies when no higher level matches and may create a case without a timeout, kick, or ban.

Higher levels use case-count thresholds. Quack counts:

- Cases in the same guild.
- Cases for the same member.
- Cases from the same template identity across all of its versions.
- Only cases that have not been voided.
- Only cases inside the template's decay window, when it has one.
- The case currently being created.

Counts are all-time by default. An admin can give a template a decay window of a number of days; cases older than that stop counting toward its escalation. They remain in the member's history, and the window can be changed later without editing any case.

Quack selects the highest threshold the count has reached. That level continues to apply to later cases until a higher threshold is reached.

For example:

```text
Default level
  Applies to cases 1 and 2
  Creates and notifies about the case

Timeout level
  Starts at case 3
  Applies to cases 3 and 4
  Creates the case and applies a 24-hour timeout

Ban level
  Starts at case 5
  Applies to case 5 and every later case
  Creates the case and bans the member
```

Escalation does not use:

- Severity labels.
- Weights or points.
- Cases from other templates.
- Cases from other guilds.
- A level chosen by the moderator.

## Starter Policy

When Quack joins a new guild, it creates one active and editable **General rule violation** template.

Its starter levels are:

| Case count | Result |
| --- | --- |
| 1–2 | Create the case and notify the member. |
| 3–4 | Create the case, notify the member, and apply a 24-hour timeout. |
| 5 and later | Create the case, notify the member, and ban the member. |

Starter cases are appealable. The starter ban removes the previous 24 hours of the member's Discord message history.

Quack shows a one-time setup notice explaining that the guild should review this template. The starter policy works immediately, but it is only a starting point. It is not a claim that every guild should moderate the same way.

## Cases

A case records that a template was applied to a member. Creating a case is itself a moderation outcome or warning. A timeout, kick, or ban is an optional additional outcome.

A case receives a human-friendly number that is unique within its guild and is never reused.

### Case state

A case is either:

- **Valid:** it contributes to the member's escalation history.
- **Voided:** it remains visible but no longer contributes to escalation.

Action progress and appeal progress are separate from case validity. A failed Discord action does not automatically void the case.

### Correcting a case

Staff cannot edit a case into a different moderation decision. The target, template, selected level, and configured action are permanent.

When a case was created incorrectly, a moderator must:

1. Void it with a reason.
2. Create a replacement case if one is needed.

This preserves both the mistake and the correction in the audit history.

### Member access

Members can see their valid and voided cases in the dashboard. Whether Quack successfully sent a DM does not control this visibility.

Member-facing case views show:

- Guild and case reference.
- Template and official reason.
- Submitted context.
- Captured evidence.
- Selected outcome.
- Appeal availability and status.
- Public case history.

They do not show individual moderator identities, internal technical details, worker information, or raw Discord errors. Staff and audit views retain exact actor identity.

## Context and Evidence

Context explains what happened. Admins define context fields on each template, and each field can be required or optional.

Supported context fields are:

- Short text.
- Long text.
- Boolean choice.
- Number.
- Discord message link.

All submitted context is visible to the affected member. Quack does not support private free-form case notes in v5.

### Capturing Discord messages

Quack supports two paths into the same evidence-capture flow:

- A moderator uses a Discord message context action on a live message.
- A moderator pastes a Discord message link in Discord or the dashboard.

When Quack can read the message, it snapshots:

- Message text.
- Author identity.
- Guild, channel, and message IDs.
- Message timestamps.
- Embed metadata.
- Attachment names, types, sizes, and original URLs.

The snapshot belongs to the case and remains understandable if the original message is edited or deleted later.

### Preserving attachments

Quack creates and manages a staff-only Discord evidence channel for the guild. It copies supported attachments into that channel and presents the copies through authorized case views.

If Discord size or file restrictions prevent a copy, Quack still stores the attachment metadata and original URL. Staff receive a clear warning that the file itself was not preserved. The case can still be created.

If a pasted link is already deleted or inaccessible, Quack explains that the snapshot failed and requires the moderator to provide the template's visible context before continuing without it.

Quack does not require external object storage for v5 and cannot promise recovery of content deleted before it was captured.

## Actions

Each level contains zero or one Discord enforcement action:

- Timeout a member.
- Kick a member.
- Ban a member.

One action per level keeps the outcome clear and avoids contradictory punishment sequences.

### Action settings

- A timeout action requires an admin-defined duration.
- A ban action may define Discord's supported message-history deletion period.
- An admin may choose the maximum number of safe automatic retries.
- Moderators cannot change action settings while applying a template.

Quack owns technical details such as execution timing, duplicate protection, internal timeouts, and error classification.

### Target safety

Normal case creation targets current human members of the guild.

Quack rejects attempts to act on:

- The moderator themselves.
- Bot accounts.
- The Quack bot.
- The guild owner.
- A member above the moderator in Discord's role hierarchy.
- A member above the Quack bot in Discord's role hierarchy.

Quack also blocks actions when the moderator or bot lacks the required Discord permission.

Special administrative flows and imported history may refer to departed users, but they are not normal template application.

## Member Notifications

A case produces at most one member notification. Quack does not send separate warning and action DMs for the same case.

The selected level decides whether to notify the member. Moderators cannot override that choice.

When notification is enabled, Quack prepares DM delivery before enforcement when necessary, then sends one message after the action result is known. This keeps the message accurate while preserving the best chance of reaching a member who was kicked or banned.

The structured message contains:

- Guild name.
- Official reason.
- Visible context.
- Moderation outcome and whether enforcement succeeded.
- Case reference.
- Appeal access when allowed.
- An optional guild-specific introduction or footer.

Admins do not replace the full message with custom code or a complex message language.

A failed DM does not invalidate or hide the case. Staff see the delivery failure, and the member can still view the case after signing in to the dashboard.

## Action Failures and Recovery

Every action attempt and result remains visible on the case and in the audit log.

Quack automatically retries only failures it knows are safe to repeat. Unsafe or uncertain failures require staff confirmation. A manual retry rechecks current Discord permission and role hierarchy.

Failed actions appear in dashboard and Discord review views with these controls:

- **Retry:** try the same configured action again when the current staff member has permission.
- **Dismiss:** remove the item from the active review queue without deleting its failure history.
- **Void case:** void the case with a required reason.

Choosing a different punishment requires a new template-based case. Staff cannot replace an action on the existing case.

## Discord Case Responses

A case created from Discord produces a public result in the staff channel where it was invoked. Validation and permission errors remain private to the moderator.

The public result shows only:

- Case number.
- Target member.
- Template.
- Selected level.
- Action status.

Detailed context and evidence remain in authorized case views instead of being copied into the channel response.

## Appeals

Appeals are part of the core case workflow. They are not template actions or optional modules.

Templates decide whether their cases can be appealed. Every appeal uses the same simple form: one question asking the member why the case should be reconsidered. Guilds do not customize it.

Members use Discord case notifications as an entry point, then submit and track the full appeal in the dashboard.

Each case has at most one appeal. Staff can reopen that appeal to request more information, but a member cannot create repeated appeal records for the same case.

Members with `Moderate Members` or higher may review appeals.

When staff accept an appeal:

1. The appeal decision is recorded.
2. The case is voided and stops contributing to escalation.
3. Any timeout or ban the case applied is queued for removal, linked to the appeal.

The removal runs only while the reviewer still has the matching Discord permission and hierarchy, and only when no other punishment of the same kind could be lifted with it. Otherwise it waits in the review queue for staff. Voiding a case any other way removes its timeout or ban the same way.

## Audit Log

The audit log is Quack's permanent moderation and administration history. It is separate from general Discord server logging.

Quack records every meaningful event, including:

- Successful and failed template or setting changes.
- Denied permission-sensitive requests. Successful reads, such as viewing a page or searching, are not recorded.
- Case creation and voiding.
- Action attempts, results, dismissals, and manual retries.
- Appeal creation, review, reopening, and decisions.
- Optional-module configuration changes.
- System actions that affect moderation data.

Audit entries are not edited or deleted. A later operation creates another entry.

All moderators can read the complete guild audit log. The dashboard provides the searchable record. A guild may also mirror important audit events to a configured staff-only Discord channel.

The audit mirror is not the same as the optional general logging module.

## Staff Statistics

Staff statistics are calculated from cases, actions, and audit history. They can show counts, trends, outcomes, and activity without creating a second source of truth.

Statistics are operational information, not leaderboards or automatic judgments about moderator performance.

## Optional Modules

The moderation core is templates, levels, cases, actions, appeals, audit history, and the statistics derived from them.

Optional modules share Quack's backend and Discord permissions, but each guild enables and configures them separately. They must not complicate the core case model.

### Tickets

Tickets provide configurable private Discord support threads between members and staff. Ticket conversations, status, and transcripts remain separate from cases and appeals.

### General logging

General logging sends configured Discord events, such as message or member changes, to staff-only Discord log channels. It does not turn Quack into a permanent searchable archive of all server activity.

General logging is separate from Quack's audit log.

### Honeypots

A honeypot detects activity in an admin-configured trap and automatically applies one selected template. The resulting case uses the normal escalation, action, notification, evidence, and audit flow.

Honeypots are the defined exception to the normal rule that staff manually apply templates.

### Other utilities

Commands such as purge, lockdown, ping, and server information may return in the future. They do not define Quack v5 and should not shape the moderation core.

## Migration From v4

Imported v4 cases are labeled historical records. They remain available for history and statistics but do not count toward v5 template escalation.

Optional modules define their own migrations when they are rebuilt. Core migration does not invent incomplete mappings for tickets, logs, honeypots, or other legacy data.

During a controlled transition, v4 and v5 may run separately without sharing moderation state. After migration, v4 direct moderation commands are removed rather than maintained as a second workflow.

## Firm Boundaries

Quack v5 is Discord-specific, even though its internal behavior is shared between Discord and the dashboard.

The following are not part of the v5 moderation model:

- Cross-guild member history.
- Public third-party automation APIs.
- Moderator-selected escalation levels.
- Direct punishment commands as an equal workflow.
- Reason overrides during case creation.
- Multiple enforcement actions on one level.
- Severity, weight, or points escalation.
- Cross-template escalation.
- Private free-form case notes.
- Hard deletion of cases or audit history.
- A separate Quack staff-role system.
- Full template configuration in Discord.
- General Discord logging inside the core audit model.

If Quack intentionally changes one of these boundaries, this document must change first. Future implementation work should cite the product rule it fulfills and treat conflicting behavior as scope drift.
